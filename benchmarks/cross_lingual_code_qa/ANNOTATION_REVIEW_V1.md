# Candidate annotation and human review protocol v1

The schema is `annotation_schema_v1.json`; the 36-query `review_candidates_v1.json` is **unverified**. It contains five candidate tasks in two repositories, each with seven EN/FR/ZH and mixed variants, plus one ambiguous-identifier query. Mixed-language text was drafted for this exercise; naturalness, meaning, labels, relevance, and identifier annotations require human review. Both repositories are currently unassigned to a split. The RepoSage examples are fixture files inside the RepoSage repository, not an independent third repository. Nothing here is approved ground truth.

Offsets are zero-based, half-open Python Unicode code-point offsets in the exact stored `text`; they are neither UTF-8 byte offsets nor UTF-16 code units. Spaces between annotated spans may be unlabeled. Language labels are human-review candidates, not calibrated classifier outputs. `code` spans carry exact symbol mentions. Preserve original bytes, punctuation and casing; when changing text, create a new revision and recompute offsets. `identifier_presence=ambiguous` is for cases a reviewer cannot reliably resolve; do not infer an identifier from every English word.

An evidence record identifies a repository-relative POSIX file path, qualified symbol, and inclusive source-line range at a pinned commit. `answer` means a candidate sufficient answer-bearing unit, whereas `context` is supporting evidence and must not automatically be scored as an equally sufficient answer. More than one answer may be accepted. Class chunks, functions, files and graph neighbors must be judged on their actual content, not name alone. Evidence coverage is a separate, index-specific observation: `not_checked` is not absence; `unknown` is not a miss. Checked results must identify a manifest containing immutable artifact hashes, repository revision, embedding model if known, and matching chunk metadata. Exact-symbol and enclosing-span coverage should be reported separately; missing exact coverage is not a ranking failure.

## Review procedure

1. Freeze the dataset version, repository commits, source-file hashes, and the review instructions. Keep the generated candidate version immutable. Provide reviewers with source at the pinned revision, the task intent and one query pair, but blind them to retrieval rankings and system identity.
2. Two independent reviewers competent in the relevant languages and code inspect each task, evidence span, query, span labels and pair. They record `accept`, `reject` or `revise`, a timestamp, a stable reviewer identifier and a concrete reason. Reviewers should not be the candidate generator and should disclose relevant conflicts. The schema checks recorded fields; it cannot verify a person's identity or independence.
3. Accept a query only if it is understandable and natural for the intended usage, expresses the same information need as its pair, preserves any requested identifier and relationship, and its language-switch labels and exact offsets are correct. Reject or revise unnatural switching, misleading identifiers, unsupported assumptions, accidental translation drift and ambiguous intent. A query need not be a literal translation, but must retain the same relevance criterion.
4. Accept evidence only after independently opening the pinned source, checking the exact path, qualified symbol and line range, and deciding whether the span itself answers the question. Mark useful but insufficient enclosing classes or callers as `context`, not `answer`. Record alternate valid answer spans and disagreements. Keep unindexable but correct evidence; do not change source judgments to fit the index.
5. If reviews disagree, mark `needs_adjudication` and have a third reviewer resolve the disagreement with a recorded reason. Preserve both original decisions. Promote a record to `accepted` only with two recorded independent acceptances; revised records need fresh review. Dataset status becomes `mixed_review` while review is incomplete and `independently_reviewed` only when every included task, query and evidence record is accepted. Rejected items remain in the review history rather than disappearing silently.
6. Only after relevance review, check coverage against a **verified snapshot**. Record exact and enclosing matches, file/line metadata and manifest identity for each evidence item and each index. Report every absent or unknown target and the scoring denominator. A parent class containing the relevant method may be context or an accepted answer depending on the reviewed judgment; do not assume either.
7. Assign entire repositories, forks and near-duplicate code families to a single development or test partition before tuning. With only these two repositories, a repository-disjoint test has inadequate diversity; recruit additional independently sourced repositories, avoid duplicate projects and verify licensing and access. Freeze held-out queries and judgments before choosing thresholds or prompts. Report reviewed and unreviewed material separately.

Check JSON Schema with any Draft 2020-12 validator, then run:

```powershell
backend/.venv/Scripts/python.exe benchmarks/cross_lingual_code_qa/validate_review_candidates.py benchmarks/cross_lingual_code_qa/review_candidates_v1.json --verify-local-source
```

The second check validates cross-record references, offsets, review-state consistency and the currently available local source ranges. It does not inspect an index, certify naturalness, validate translation meaning, verify reviewer identity, or replace human adjudication. The existing controlled evaluator uses a different toy schema; an explicit reviewed-data adapter and index-coverage pass are required before this schema can support research evaluation.
